> ①产品/信息架构 ②读者（内容消费体验）③手机/桌面用户 ④无障碍 ⑤性能 ⑥工程维护 ⑦答辩现场

## 视角一：产品 / 信息架构 —— 最亏的是「内容有、入口没有」

这是本轮最值得动的一类问题：**不是缺功能，而是已经躺在库里的内容没有出口。**
和之前三个 P0（图片路径 / 请求失败 / 回复读错字段）是**同一个家族**：东西是好的，只是没被消费。

### A1 🚨 六个板块只有两个有入口

线上 `/api/boards` 实测（2026-09-17）：

| 板块 | 帖子数 | 小程序入口 |
|---|---|---|
| 攻略心得 | 155 | ✅ 首页「推荐攻略」→ `list?boardId=1` |
| 资讯速递 | 99 | ✅ tabBar「资讯」 |
| **玩家天地** | **152** | ❌ 无 |
| **其他** | **117** | ❌ 无 |
| **游戏吐槽** | **109** | ❌ 无 |
| **二次创作** | **69** | ❌ 无 |

代码证据：全项目对板块的引用只有两处 ——
`pages/news/news.vue:65`（`BOARD.NEWS`）与 `pages/game/detail.vue:68`（`BOARD.GUIDE` / `BOARD.NEWS`）。

⇒ **447 帖（占 701 的 64%）在小程序里没有任何入口。** 而这一轮内容富化的重点
「8 场 23~27 回复的长讨论串」，从内容气质看大概率落在玩家天地 / 游戏吐槽，也就是说
**这轮最值钱的内容，小程序一条都到不了。**

**建议（成本极低）**：`pages/list/list` 本来就是通用的板块流（`boardId` 参数已支持），
所以这是**纯新增入口**、不用写新页面：
- 最小版：首页加一个「🔥 热门讨论」模块（`fetchPosts({ boardId: 3, sort: HOT, size: 5 })`）；
- 完整版：`资讯` 页顶部的 chip 行从「只有排序」扩展成「板块 × 排序」，或新增一个「板块」入口页。

> ⚠️ 这条与 `docs/方案设计.md` §二「范围界定」有张力：方案里明确砍掉了社交链路。
> 但**「看讨论」不等于「参与讨论」** —— 它仍在「内容消费」范围内，只是把消费面从
> 攻略+资讯扩到全站内容。**要不要做、做到哪一档，需要你拍板**（我倾向：先加首页一个模块）。

### A2 🚨 公告有正文，页面只给标题，而且点不动

- 线上 `/api/announcements` 实测 **5 条**，字段包含 `title` / `content`（首条 100+ 字）/
  `isTop` / `creatorName`（首条是「YUMU 游戏社区上线公告 & 社区公约」，管理员发布）。
- 代码 `pages/news/news.vue:4-9`：只渲染 `a.title`，**没有 `@click`**；
  且该文件第 3 行的注释还写着「⚠️ 线上当前 0 条」——**注释已过期**（内容富化时补上了公告）。

⇒ 用户看到「📢 公告 / YUMU 游戏社区上线公告 & 社区公约」，点一下**没有任何反应**，
而正文其实就在响应里。观感上很像「公告功能坏了」。

**建议**：点标题弹层渲染 `content`（`uni.showModal` 放不下长文，用一个底部抽屉或跳
`pages/post/detail` 的通用详情页更合适）；同时把注释改成事实。

### A3 ⚠️ 搜索「综合」把两类结果悄悄丢了

实测 `/search?keyword=艾尔登&type=all` 的 `data` 结构是
`{ posts, boards, users, games }` 四类。而：

- `pages/search/search.vue` 的 `types` 只有 `综合 / 帖子 / 游戏` 三个 tab（后端支持 `board` / `user`）；
- `type=all` 分支只取 `res.games` 与 `res.posts`，**`boards` / `users` 直接丢弃**（连「还有 N 条」都不提示）。

**建议**：`综合` tab 下若 `boards/users` 非空，补两行轻量结果（板块名 / 用户名 + 跳转）。
这既是补全，也顺手把「静默丢弃」的老毛病堵上。

### A4 ⚠️ 游戏库只筛平台，不筛类型

实测 80 款游戏的分布：

- 平台：`多平台 39 / PC 19 / 手机 16 / 主机 6`（UI 只有这 4 个 chip ✅）
- 类型：**31 种**（`RPG 13 / MMORPG 5 / 策略 5 / ACT 5 / 开放世界 4 / 动作 4 / 模拟经营 4 …`）→ **UI 无入口**

而 `fetchGames` 早就支持 `genre` 参数（`api/community.js:20`），后端也支持。
⇒ 用户想找「魂类 3 款」只能一页页翻。

**建议**：加一行类型 chip。31 种太多 → 取帖子/游戏数 Top 8 + 一个「更多」；
或做成两行「平台 | 类型」，保持现有 chip 视觉。

### A5 ⚠️ 首页缺一个「每日精选」位，而接口是现成的

- `/api/picks/daily` 线上返回 **3 条**，且字段比列表丰富：`authorAvatar` / `authorLevel` /
  `authorLevelTitle`（如「⚔️活跃玩家」）/ `authorBadge` 等。
- `api/community.js:91` 的 `fetchDailyPicks` **零调用**（死代码）。

⇒ 首页现在是「热门游戏 / 最新资讯 / 推荐攻略」三块，全是**列表**，没有「今天看什么」的编辑感。
每日精选正好补上，且能顺带展示作者等级这类社区味字段。

### A6 ⚠️ 79 款游戏有发行商，页面上一个都没有

- 实测：`publisher` 有值 **79/80**，`releaseDate` 有值 **79/80**，`description` **80/80**。
- `pages/game/detail.vue` 的游戏头只渲染 `platform` / `genre` / `releaseDate`，
  **`publisher` 从未出现**（首页卡片、游戏库列表也没用）。

⇒ 80 个游戏详情页长得几乎一样（名称+简介+三个 chip），信息量偏薄。
补一行「发行商 · 发售日 · N 篇攻略（`postCount`）」成本几行，页面立刻厚实。

### A7 💡 四个接口定义了但没人调用（死代码）

| 函数 | 位置 | 现状 |
|---|---|---|
| `fetchDailyPicks` | `api/community.js:91` | 0 调用 → **A5 正好用** |
| `fetchGameActiveUsers` | `api/community.js:31` | 0 调用 → 可做「活跃玩家」 |
| `fetchTagPosts` | `api/community.js:73` | 0 调用 → 可做标签流 |
| `fetchBoards` | `api/community.js:67` | 0 调用 → **A1 正好用** |

⇒ A1/A5 落地后这 4 个里的 2 个自然复活；剩下的要么用、要么删，别留着当噪音。

## 视角二：读者体验 —— 拆解卡很亮，但「读完就断」

拆解卡确实是这端的核心亮点（保全率 86.1% → 97.1%，回归 25 项单测盯着它），
但**一篇读完之后没有下一步**，这会让 20 篇长文 + 8 场讨论串的价值打个对折。

### B1 ⚠️ 详情页没有「下一篇 / 相关推荐」

`pages/post/detail.vue` 的结尾是：正文 → 标签 → 回复 → 底部「收藏 / 分享」。
**没有任何纵向推荐**。用户的唯一出路是点返回。

**建议**：底部补一个「同游戏更多攻略」（`fetchGamePosts(post.gameId, {boardId:1})`，
去掉当前帖）或「同板块热门」。1 个请求、复用 `PostCard`，把「一篇」变成「一条线」。

### B2 ⚠️ 正文图片不能点开看大图

全项目没有 `uni.previewImage`（grep 零命中）。攻略里的装备图、关卡图在手机上调不出细节。

**建议**：给 `.content__img` 加 `@click="uni.previewImage({ urls: allImgs, current: i })"`。
几行代码，演示时手感提升明显。

### B3 💡 阅读辅助缺失（长文的「阅读器」属性还没做出来）

- 无字号调节（16 张卡的长文，小屏吃力）；
- 无目录（拆解卡有 `section` 分组，天然可以生成锚点目录）；
- 无阅读进度。

这三条属于「有则加分、无则扣分」的阅读器基本功。建议至少做**字号三档 + 目录**（分组数据已在 `cards[].showSection` 里，不用重新解析）。

### B4 💡 讨论串只读是对的，但可以给一条「去社区参与」

本端不登录是明确的设计取舍（`我的` 写「访客模式」而非「未登录」，很得体）。
但读完 27 条讨论串、有话想说时是**死路**。

**建议**：回复区底部加一行弱化的「想参与讨论？去 YUMU 社区 →」（跳主站 Web）。
不破坏「不做社交」的边界，还把 H5 流量导回主站，答辩时是一个漂亮的收口叙事。

### B5 ⚠️ 收藏列表是「快照」，且失效不可见

`utils/store.js` 收藏时只存 `id/title/boardName/gameName/likeCount/at`。
帖子被删或改名后，本地条目仍是旧标题，点进去 404 —— **页面上没有任何失效标记**。

**建议**：`我的` 页在 `onShow` 时对当前可见条目做一次轻量校验（或点进去 404 时自动打标「已失效」并给「移除」按钮）。

## 视角三：手机 / 桌面用户 —— **H5 是主交付渠道，却在宽屏上全程拉伸**

这条我认为是本轮**性价比最高的修复**，因为 H5 恰好是写进 README 的「主交付」。

### C1 🚨 实测：桌面打开，卡片被拉成 3.91 倍

`tests/probe-review.cjs` 打线上（`http://8.133.255.202/m`）实测：

| 视口 | `.mp-page` 宽 | 帖子卡宽 | 标题可用宽 |
|---|---|---|---|
| 390×844（手机） | 390 | 361 | 185 |
| 768×1024（平板） | 768 | 711 | 367 |
| **1440×900（桌面）** | **1440** | **1412** | **1243** |

**拉伸比 3.91×**。标题行可用宽 1243px ≈ **一行上百个汉字**，正文更是全宽铺开。
代码侧印证：全项目 `@media` **0 个**、页面级 `max-width` **0 个**。

⚠️ 现实风险：**答辩若用笔记本打开 `/m/`（大概率），第一屏就是这个观感** —— 看起来像「布局没做」，
而不是「移动端设计」。这条比任何功能缺失都更影响第一印象。

**建议**（`#ifdef H5` 条件编译，不影响小程序端）：

```css
/* #ifdef H5 */
.mp-page { max-width: 750rpx; margin: 0 auto; }
/* 更彻底：宽屏双列 */
@media (min-width: 900px) { .mp-page { max-width: 1100px; } /* 卡片两列 */ }
/* #endif */
```

另外 tabBar 在宽屏也应居中（固定 750rpx 宽居中），否则四个 icon 会散在 1440px 两端。

## 视角四：可访问性 —— 两处硬指标不达标

### D1 ⚠️ 对比度不达 WCAG AA

探针实测（深色底 `#1a1725` 卡片上）：

| 元素 | 颜色 | 字号 | 对比度 | AA 要求 |
|---|---|---|---|---|
| `.pc__title`（标题） | `#e9e7f2` | 15.6px | 14.4:1 | ≥4.5 ✅ |
| `.pc__summary`（摘要） | `#8b8599` | 13px | 4.96:1 | ≥4.5 ✅ |
| **`.pc__meta`（时间/赞/回复）** | `#6f6a80` | **11.44px** | **3.39:1** | ≥4.5 ❌ |
| **`.gcard__meta`（游戏帖数）** | `#6f6a80` | **10.92px** | **3.39:1** | ≥4.5 ❌ |

`#6f6a80` 在项目里出现 **28 次**，是「弱化文字」的主色。
深层问题：`App.vue` 定义了 `--c-text-3: #6f6a80` 这个语义，于是**一处偏暗 = 全站偏暗**。

**建议**：提亮到 ≈`#8f8aa4`（同底 ≈4.6:1），一次性解决 28 处。
顺带把 `--c-text-2`（`#8b8599`，4.96:1）保持不动即可。

### D2 ⚠️ 40 个 `<image>` 全部没有 `alt`

探针读数：`<image>` 元素 **40 个，其中无 alt 40 个**（渲染后真 `<img>` 22 个无 alt）。
`<image>` 在小程序与 H5 都支持 `alt`。对纯图片内容端来说，这是最基础的一条。

**建议**：`GameTile` / `PostCard` / 正文图片统一补 `:alt="名称"`（组件级改一处，全站生效）。

### D3 💡 两个按钮高度 34px

首页 banner 的「逛游戏库 / 看资讯」实测 **34px < 44px**（iOS HIG 建议值）。只有 2 处，一行 padding 可修。

### D4 🚨 主题令牌形同虚设（这是所有视觉债的根）

- `App.vue` 定义了 **13 个** `--c-*` 令牌（`--c-bg` `--c-card` `--c-primary` `--c-text-3` …）；
- 全项目对这些令牌的引用：**0 次**（`grep -rn 'var(--c-' pages components App.vue` → 0）；
- 硬编码十六进制色值：**175 处**。

而且已经**漂移**出四个语义相同的近似灰：

| 色值 | 次数 | 语义 |
|---|---|---|
| `#8b8599` | 14 | 次级文字（= `--c-text-2`） |
| `#c8c3d6` | 6 | 次级文字（不在令牌表里） |
| `#b9b3c9` | 1 | 次级文字（不在令牌表里） |
| `#cfcade` | 2 | 更亮一点的次级文字（不在令牌表里） |

**后果**：改品牌色要改几十处；想做浅色模式基本等于重写；「弱化文字」到底多弱没人说得准。

**建议**：一次性收敛（可脚本化 `sed` 替换 → 人工复核），
并把 `#c8c3d6 / #b9b3c9 / #cfcade` 三个野色值归并到 `--c-text-2` / `--c-text-3` 两档。
**做完 D4 再做 D1，只需改一个变量值。**

## 视角五：性能 —— 首屏 328KB，图片占 62%，且无懒加载

探针在手机视口（390×844）实测首屏：

| 类别 | 数量 | 传输量 |
|---|---|---|
| JS | 7 | 94.2 KB（最大 `index-wyoCTqZE.js` **85.8 KB**） |
| CSS | 7 | 10.3 KB |
| **图片（`/api/files/*`）** | **18** | **202.5 KB** |
| 其它 | 10 | 21.4 KB |
| **合计** | 42 | **≈328.5 KB** |

DOMContentLoaded 235ms，首屏 `<image>` 40 个、DOM 节点 466 —— 都不算重，**结论是首屏很健康**。

真正的问题在**后面**：

### E1 ⚠️ 全项目没有 `lazy-load`

`grep -rn 'lazy-load\|lazyLoad' pages components` → **零命中**。
列表页一次 10~12 条、每条约 13~17KB 缩略图，实测游戏库上拉后卡片数 **12 → 60**
（`verify-miniprogram.cjs` 的 C4），也就是说**翻三页就多拉近 1MB 图**。
而库里有 701 帖 / 80 游戏，长列表是常态。

**建议**：
1. `<image lazy-load>`（`<image>` 原生属性，一行）；
2. 缩略图与正文图用**不同地址**——若后端 `/api/files/` 支持尺寸参数则列表走缩略图（**需先确认**，后端是主站会话的领地，得先查清再动）；
3. 正文图片按需（进入视口才加载）。

### E2 💡 零缓存：切 tab 回来整页重拉

首页 `onLoad` 并发 4 个请求；tabBar 切走再回来会重新走一遍（`onShow` 未做缓存）。
对「内容消费」场景，**stale-while-revalidate 体验**（先出旧数据、后台刷新）值得做：
`utils/store.js` 已经在做本地存储，加一层带 TTL 的列表缓存即可。

## 视角六：小程序端原生能力 —— 受「不上架」约束，按取舍看

先说结论：**受限于不上架（需 HTTPS 备案域名 + 小程序 ICP 备案），
订阅消息 / 客服消息 / 支付 / web-view 这些都不可用，属于范围外，不该做。**
能优化的是「即使只在开发者工具 + 真机预览里演示，也值得有」的部分：

| 项 | 现状 | 建议 |
|---|---|---|
| **F1 分享** | 只有 `pages/post/detail.vue:350` 一个 `onShareAppMessage`；游戏详情 / 首页 / 列表页都没有；**无 `onShareTimeline`**（朋友圈） | 游戏详情页补一个（分享游戏页比分享帖子更有传播力）；H5 端已是「复制链接」，可补一条「在微信里打开可转发」的提示 |
| **F2 分享卡片图** | 用默认截图 | 可选：`imageUrl` 指定游戏封面，分享卡片更好看 |
| **F3 PWA / 添加到桌面** | H5 无 manifest | 可选小加分（答辩讲「H5 也能装到桌面」） |
| F4 订阅消息 / 客服 | — | ❌ 需登录 + 服务端，范围外，不做 |

## 视角七：工程与交付 —— 三处「同族老毛病」还没清完

### G1 ⚠️ 收藏超过 200 条会**静默丢弃**

```js
// utils/store.js
const MAX_FAVORITES = 200
write(STORAGE_KEYS.FAVORITES, list.slice(0, MAX_FAVORITES))   // 第 201 条起，最老的无声消失
```

这和三个 P0 是**同一个家族**：没有报错、没有提示，用户只是**不知不觉少了东西**。
浏览历史 `MAX_HISTORY = 50` 同理（历史丢一点可接受，收藏丢绝对不可接受）。

**建议**：上限提到 500，且**触顶时明确提示**「收藏已达上限，最早的收藏将被移除」；
或按 `at` 排序后丢弃并记一个 `droppedAt`，在「我的」页给一行说明。

### G2 ⚠️ 为「首屏并发」设计的 `silent`，一次都没被用上

`api/request.js:50` 的注释写着「静默模式：失败不弹 toast（**用于首屏并发拉取**）」，
但 `grep -rn 'silent'` 的结果是——**只有 request.js 自己**。
首页 `load()` 并发 4 个请求，全部走默认 `silent = false` ⇒ 断网时 4 个失败各弹一次
「网络异常，请稍后重试」（`uni.showToast` 会互相覆盖，表现为 toast 抖动多次）。

**建议**：把首页/列表首屏的并发拉取改成 `{ silent: true }`，失败统一由 `ErrorState` 表达
（这恰好也符合「失败 ≠ 空数据」那条工程约定：失败由失败态说话，不用 toast 重复喊）。

### G3 ⚠️ README 有两处过期事实

- 第 143 行：「**47 款游戏全部有 `cover`**」→ 实际 **80 款**（内容富化后）；
  这行的语境本来是「提醒别照抄旧注释」，结果自己成了旧注释。
- 第 172 行：`POST /posts/{id}/tags` → 实际是 **GET**（代码里就是 `get`）。

### G4 💡 回归入口分散，建议收成一个命令

现在是 4 条命令（`stepParser.test.mjs` + `content.test.mjs` + `build:h5` + `verify-miniprogram.cjs`）。
建议在 `package.json` 加：

```json
"verify": "node --experimental-default-type=module tests/stepParser.test.mjs && node --experimental-default-type=module tests/content.test.mjs && npm run build:h5 && node tests/verify-miniprogram.cjs",
"verify:live": "MP_BASE=http://8.133.255.202/m node tests/verify-miniprogram.cjs"
```

好处：答辩前一键自检；将来接 CI 只差一个 runner。

### G5 💡 5 个 `dist_bak.*` 目录留在子项目里

发版时绕过删除守卫留下的备份（`miniprogram/dist_bak.2026*.…`，共 5 个）。
它们不在 git 里（`.gitignore` 已忽略），但会**污染 Docker 构建上下文**的统计口径，
也没必要长期留着。建议清理（发版链路本身没问题，是本地残留）。
