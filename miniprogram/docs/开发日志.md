## Day 2 ｜ 2026-09-16 ｜ 交付路线定案：**不上架**

**问题**：能不能像网页那样「买个服务器就上线使用」，不买域名、不做备案，只要不传播就行？只用于简历与毕设展示。

**核实结论（查官方文档 + 平台规则）**

1. 🚫 **「上架」这条路是堵死的**，且是两道锁而非一道：
   - **锁一：服务器域名不接受 IP**。小程序「服务器域名」必须填 **HTTPS 域名**，不支持 IP、不支持端口 ⇒ 现有 `http://8.133.255.202/api` 连配置入口都过不去。
   - **锁二：小程序自身也要 ICP 备案**。2023-09-04 起新增小程序**须完成备案才能上架**，未备案提交发布返回 `errcode 86369「小程序上架需先完成备案」`。个人主体可备案（上限 5 个），但**名称与服务内容不得涉前置审批领域**（含「新闻 / 网络文化 / 出版 / 游戏」等）——「游戏资讯」很容易撞上新闻类前置审批。
   - 叠加第三层：个人主体类目受限，且不能做论坛/社区，需把定位表述为「工具」类。
2. ⚠️ **「不传播就没事」这个假设不成立**。备案义务取决于「是否在境内提供互联网信息服务」，与传播范围无关；只是现实执行层面单机/演示用途通常不会被追究（阿里云已从技术上把未备案域名的 Host 头拦掉）。
3. ✅ **但「展示」根本不需要上架**。三条路都绕开备案：
   - **H5 版挂现有服务器**（最推荐）——手机浏览器打开 IP 即可，**完全不受小程序规则约束**。
   - **开发者工具 / 真机预览**——直连 IP；真机预览需在右上角菜单**打开调试**才跳过合法域名校验（官方文档口径）。
   - 体验版——**不需要小程序备案**，但请求仍走合法域名校验，因此仍需 HTTPS 已备案域名 ⇒ **不采用**。

**产出**

- `docs/方案设计.md` §七重写为三层：**7.1 交付路径（已定）** / 7.2 上架四道关卡（记录备查）/ 7.3 其余限制；§十「是否需要正式发布」标记为已决。
- `miniprogram/README.md` 新增「交付方式（已定：不走上架）」章节；「三条硬约束」扩为**四条**（第 4 条 = 不上架）。

**口径（重要）**

- 简历 / 答辩统一表述：**「完成小程序端开发，并通过 H5 版本部署上线」**。**不得写「小程序已上架」**——与既有的诚实原则一致。

## Day 3 ｜ 2026-09-16 ｜ 骨架 + 请求层 + 全量页面：**双端构建 + 27 项浏览器回归全绿**

**前提确认（用户答复）**：老师**没有**要求原生小程序，只说「要微信小程序前端」。
⇒ 按 uni-app 走 —— 编出的产物**本身就是真正的微信小程序**（实测产物含 13 个 `.wxml` / 14 个 `.wxss` / 15 个 `.json`），H5 只是**额外**多出的一条交付渠道。**一鱼两吃，且满足老师的硬要求。**

### 一、工程骨架（`miniprogram/` 作为独立子项目）

```
miniprogram/            ← 与 backend/ frontend/ 平级
├── package.json        uni-app CLI 工程（根）
├── vite.config.js      /api 代理 → 线上后端（开发期）
├── index.html
├── src/                uni-app 源码
│   ├── main.js  App.vue  pages.json  manifest.json
│   ├── api/            config.js（端点单一来源）· request.js · community.js
│   ├── utils/          format.js · content.js · stepParser.js · store.js
│   ├── components/     GameTile · PostCard · StepCard · EmptyState · Skeleton
│   └── pages/          index · games · game/detail · news · post/detail · my · search · list
└── tests/              单测 + 浏览器回归 + 产物验证服务器
```

**关键配置决策**

- **`vite` 锁定 `5.2.8`（精确版本）**：`@dcloudio/vite-plugin-uni` 的 `peerDependencies` 就是 `"vite": "5.2.8"`，写成 `^5` 会装出不一致版本。
- **uni CLI 入口在 `@dcloudio/vite-plugin-uni`**（`bin/uni.js` 提供 `uni` 命令），版本 `3.0.0-5020420260813003`（Vue3 线；注意 `latest` 指的是 Vue2 线）。
- **H5 用 hash 路由 + `base=/m/`**：hash 模式下部署只需把 `dist/build/h5` 拷到 nginx 的 `/m/` 目录，**不需要 `try_files` 回退**，改动面最小。
- **端点用条件编译区分**（`src/api/config.js`）：H5 走相对 `/api`（与后端同源）；小程序走绝对 `http://8.133.255.202/api`。**两处地址只在这一个文件里出现。**

### 二、实测发现（都是会影响正确性的事实，逐个查过）

1. 🚨 **全库零封面图**：线上 **18 款游戏的 `cover` 全部是 `null`**，帖子封面也全部为空（扫 36 篇 0 命中），**只有用户头像有图**（`/api/files/*.png`）。
   ⇒ 游戏卡**默认形态就是「首字渐变色块」**（按 id 取模稳定取色），有图才显示图。反过来写会让所有游戏卡变空白。原型里恰好就是这个设计。
2. 🚨 **帖子总量是 36 篇，不是记忆里的「133 篇」**：6 个板块各 6 篇；`/announcements` 与 `/picks/daily` 均为 **0 条**。⇒ 内容偏薄，是当前最需要处理的问题（见「遗留」）。
3. ✅ **`/api/files/**` 的 GET 是公开的**：用 `curl -I`（HEAD）探测会得到 **401**，容易误判成「图片要鉴权」。实际放行规则只写了 `GET`，**HEAD 不在列表里**。图片用 `<image>` 加载走 GET，不需要 token。
4. **平台筛选有效**：`platform` 取值实测为 `多平台`(6) / `手机`(6) / `PC`(5) / `主机`(1)；`genre` 有 12 种但每种 1–3 款，**故只做平台筛选**，类型以标签展示。
5. **搜索支持 `type=game`**（文档只写了 `all|post|board|user`）；`type=all` 返回 `{posts: PageResult, boards, users, games}`。

### 三、核心亮点：步骤卡 → **升级为「阅读拆解」**

**遇到的问题**：把解析器拿到线上真实内容上实测 —— **0/36 篇能切出步骤**。真实内容**全是「一整段散文」**，没有任何序号（如「前期…中期…逆风…」被写成了一个段落）。照原设计，这个亮点在演示时**一个帖子都看不到**。

**解决**：在原三条规则后补第四条 **「要点拆分」**，并对结果打标 `kind`：

| 规则 | 触发条件 | 产出 |
|---|---|---|
| 1. 显式序号 | `第一步` / `①` / `1.` / `1、` / `（1）` / `Step 1` | `kind=step` |
| 2. 小标题 | `## xxx` / `【xxx】` | `kind=step` |
| 3. 多段兜底 | 段落数 > 3 | `kind=step` |
| **4. 单段多句** | **段落 ≤ 3 且句子 ≥ 3** | **`kind=point`** |

页面据此把切换按钮渲染成「**要点模式 / 原文模式**」（有真步骤时才叫「步骤模式」）。**后端依然一行不改**，且给将来落库留了演进路径。

**实测效果**：拆解率 **0/36 → 24/36**；「攻略心得」板块 6 篇全部切出 3 张卡。

> 细节：要点模式下**不写「要点 N」当标题** —— 卡片左侧本来就有序号圆圈，正文里再写一次是冗余；有「前期思路：…」这类天然分隔时冒号前提为标题。

### 四、验证（两层，共 47 项断言）

- **解析器单测 20/20**（`tests/stepParser.test.mjs`）：6 种序号形态 + 2 种小标题 + 分段兜底 + 3 种要点拆分 + 5 项「必须退化为 null」+ 3 项 HTML（含 `<script>` 注入被剔除）。
  - ⚠️ 源码是 ESM 但 `package.json` 无 `"type": "module"`（uni-app 惯例），故需 `node --experimental-default-type=module` 才能**直接 import 被测源码**；**代价是源码内相对导入必须带扩展名**（`./content.js`）。
- **浏览器回归 27/27**（`tests/verify-miniprogram.cjs`，打在**真实构建产物**上）：首页 / 详情页（要点卡、模式互切、收藏切换）/ 游戏库（列表、平台筛选、**上拉加载 12→18**）/ 资讯 / 我的 / 搜索 / 全局无 JS 报错。
  - 产物验证靠 `tests/serve-h5.mjs`：把 `dist/build/h5` 挂在 `/m/` 并把 `/api` 代理到线上 —— 否则相对路径 `/api` 没有后端，页面全空数据。
  - 复用社区项目已装的 `playwright-core`（`NODE_PATH` 指向 `tests/.pw/node_modules`），不重复安装。

**这一轮踩到并记录的坑**

- 🚨 **`page.goto` 只改 hash 不会重新加载文档**：SPA 会带着上一节的状态继续跑，导致「上拉加载」一节**假失败**（还停在上一节的 PC 筛选，5 条已是全部）。修法：URL 加一个变化的 query 强制整页重载。
- **uni-app H5 的滚动容器是 `documentElement`/`body`**（`uni-page-body` 自身 `scrollHeight == clientHeight`，不滚）；要滚到 `documentElement.scrollHeight` 才会触发 `onReachBottom`。
- **重复 `npm run build` 会撞宿主的批量删除守卫**（Vite 清 `dist`）：先用 PowerShell 把 `dist` 移走再构建。
- 先写**量化探针**（`tests/probe-scroll.cjs`）再下结论：本次正是靠它证明「上拉加载本身是好的，是测试写法有问题」，避免去改没有 bug 的业务代码。

## Day 4 ｜ 2026-09-17 ｜ **H5 上线** + 三类「只在生产暴露」的问题

目标就是补上计划里的最后一步。结果：**<http://8.133.255.202/m/> 已可访问**，代码入库，回归从 27 项扩到 **28 项**、**线上实跑 28/28 全绿**。

### 一、上线方式：搭现有发版链路，不新增任何设施

`deploy/tools/deploy-local.sh` 原来发前端时只跑 `frontend` 的 `npm run build`。现在多一步：

```
npm run build:h5  →  产物拷进 frontend/dist/m/  →  随同一个 nginx 镜像上线（COPY frontend/dist）
```

于是 `/m/` 由 nginx 现成的 `location /` + `try_files` 就能服务（H5 是 hash 路由，不需要深层回退），
**nginx 配置一行都没改**。H5 构建失败**不阻断发版**（附加渠道不拖累主站），但会在第 7 步验收里被检查。

### 二、本轮修掉的四个问题（都不是"写完就好"的那种）

| # | 问题 | 后果 | 关键点 |
|---|---|---|---|
| 1 | **改动判定不含 `miniprogram/`** | 「只改小程序」被判成无需重建 → 产物推了、镜像没重建，**线上 `/m/` 静默停在旧版** | 这个判定**本机与服务端各有一份**，只修一处等于没修 |
| 2 | **`git bundle` 回退路径失效** | GitHub 被墙时唯一的代码同步通道直接报错，发版中止 | 路径写成 `/e/...`（MSYS 形式），Windows 版 git 认不了；但 `tar/scp` 能认，所以只在 git 这步炸 |
| 3 | 🚨 **H5 模板内联脚本被生产 CSP 拦死** | **真机上没有 viewport meta** → 按 980px 桌面宽度渲染，移动端布局全乱 | 见下节，本轮最有价值的发现 |
| 4 | 回归只测本地、不带安全头 | 问题 3 本地全绿、上线才炸 | 给 `serve-h5.mjs` 补上**生产同款五项安全头** |

> 问题 1 的表现特别值得记：两边都在打印**成功** ——
> `✅ 前端 dist 已送达并校验 bundle 一致` / `⚠️ 这次改动只涉及脚本/文档/备份等，不需要重建任何容器`。
> **"每一步都成功、整体却是错的"**，正是本项目一直在防的那类故障。

### 三、问题 3 的完整因果（值得讲清楚）

uni-app 官方 H5 模板的 `index.html` 里有一段**内联脚本**，用 `document.write` 生成 `<meta viewport>`
（目的是在支持 `env()` 的设备上才加 `viewport-fit=cover`，做刘海屏适配）。

而本站 nginx 的 CSP 是 `script-src 'self'`（`security-headers.conf` 里明写「前端无内联脚本」）：

```
Refused to execute inline script because it violates CSP directive: "script-src 'self'"
```

脚本被拒 ⇒ **`document.write` 从未执行** ⇒ 页面上**一个 viewport meta 都没有** ⇒
真机浏览器按 980px 桌面宽度渲染。

**为什么它差点溜过去**：页面不白屏、功能也都正常，只是控制台多了几条报错。
要不是把回归直接打在**线上真产物**上，这一条会被当成噪音忽略。

**修法**：`index.html` 换成**静态** viewport meta（`viewport-fit=cover` 直接写死，旧浏览器忽略该属性）；
`serve-h5.mjs` 复刻生产五项安全头，让本地就能复现 CSP 约束。
**并且给回归加了 G3 直接断言 viewport meta** —— 后果这么重的问题，不能只靠"有没有报错"来发现。

### 三、本轮最值得记的一条：H5 的 `<image>` 会被路由 base 污染

`<image>` 发出的地址变成了 `/m/api/files/seed_post_200408.jpg`（多了一段 `/m/`）：

- 本地：静态服务器没有这个路径 → 404
- 线上：主站 SPA 的 `try_files → /index.html` 回退把它兜成 `text/html`
  → 解码失败（**注意不是 404**，看状态码会误判成"图存在但格式不对"）

根因：**uni-app H5 的 `<image>` 组件按 `manifest.h5.router.base`（本项目 `/m/`）解析根相对路径**。
双向对照锁死了责任方：同一文档里普通 `<img src="/api/files/x.jpg">` 完全正常，
所以**与 nginx / 后端无关**，改的只是前端的 `ASSET_BASE`（改为 `location.origin` 出绝对地址）。

**为什么回归全绿却没人发现**：原来的 28 项断言里**没有一条验证图片真的解码成功**，
而 `@error` 兜底又把「图挂了」渲染成「正常的首字色块」—— 页面看起来一切正常，就是光秃秃。
现在补了两条硬断言：

- **G4a**：全程不允许出现 `/m/api/files/*`（直接盯住这个 bug 的形状）
- **G4b**：`/api/files/*` 的响应必须**全部** 200 且 `content-type: image/*`

> 记一笔环境事实：`uni-app` H5 的 `<image>` 渲染成 `<uni-image><div style="background-image:url(...)">`，
> **不是 `<img>`**，所以 `naturalWidth` 那套查法在这里没用 —— 判据要落到**网络响应**上。
> 反过来，tabBar 图标是真 `<img>`，可以用 `naturalWidth > 0`（G5b）。
