## 二、从源码构建 / 启动

### 2.1 后端（Spring Boot）

```bash
cd backend
mvn clean package -DskipTests        # 产出 target/yumu-community-1.0.0.jar
java -jar target/yumu-community-1.0.0.jar
```

- 默认端口 8080；接口前缀 `/api`。
- 需要 MySQL（库 `yumu_community`）+ Redis。本机起：`cd backend && java -jar target/*.jar --server.port=8080`。
- 已部署线上版：`http://8.133.255.202/`（无需本地起，小程序默认连它）。

### 2.2 小程序（uni-app + Vue3）

```bash
cd miniprogram
npm install

npm run dev:mp-weixin      # 开发模式（热更新）
npm run build:mp-weixin    # 生产构建 → dist/build/mp-weixin
npm run build:h5           # H5 版 → dist/build/h5（已并入线上 /m/）
```

> 🚨 **关于 AppID（2026-09-27 起已自动处理）**
> `miniprogram/src/manifest.json` 里的 `mp-weixin.appid` 是**空字符串** —— 这是「AppID 不进版本库」的
> 安全约定，不是遗漏（2026-09-18 曾因硬编码 AppID 触发 GitHub 密钥扫描告警）。
> 本机 `miniprogram/.env.local` 里存有真实 AppID（**该文件属个人凭据，不随交付包发布**）；
> `npm run build:mp-weixin` 会在构建完成后**自动**把它写进**产物**
> `dist/build/mp-weixin/project.config.json`，源码 manifest 全程不碰 ⇒ 不会泄漏，也不必手动还原。
> **换一台机器**：新建 `.env.local` 写一行 `WX_APPID=你的appid` 再构建即可（也可用微信公众平台的**小程序测试号**）。
>
> 🚨 **别用 `npm run build:mp-weixin:raw`**（它是裸构建，产物 appid 为空）：
> 微信开发者工具读到空 appid 会**自动降级成 `touristappid`（游客模式）**，此时工具栏
> 「预览 / 真机调试 / 上传」**三个按钮全部变灰、点了没反应**（模拟器里却一切正常，很容易误判成工具故障）。
> 自查一行：`grep '"appid"' dist/build/mp-weixin/project.config.json` —— 必须是 `wx` 开头。

## 五、已实现功能范围

**产品定位**：多平台游戏攻略与资讯的**聚合与分类展示端**（小程序）；后端是完整的社区后台（用户 / 内容 / 权限 / AI 助手）。

### 小程序端
- **内容聚合**：只收 **攻略心得（155 篇）+ 资讯速递（128 篇）= 283 篇**干货；游戏吐槽 / 玩家天地 / 二次创作 / 其他 四个板块合计 446 篇不进小程序（产品口径，非技术限制）。
- **平台筛选（主交互）**：顶部一排平台按钮（全部 / 多平台 / PC / 主机 / 手游），每个按钮带该平台的**真实篇数**。
- **游戏库**：按游戏聚合，卡片显示该游戏的**攻略 + 资讯篇数**（与详情页实际条数一致）。
- **攻略详情**：正文阅读 + **相关攻略**推荐；不设回复区（弱化互动）。
- **互动**：点赞 / 收藏 / 分享（分享对游客开放）。
- **登录注册**：账号与主站完全通用（同一套用户表与接口）；支持忘记密码、注册协议勾选。
- **举报**：详情页可提交举报；管理员 / 版主可在端内「举报处理」页直接结案（见下方权限方案）。
- **资讯页**：官方资讯展示，带「置顶 / 官方 / 精华」角标。
- **游客只读**：未登录可正常浏览与筛选；点赞 / 收藏 / 举报先引导登录（不静默失败）。
- **🔐 权限方案（三层体现，可操作、可对比）**：RBAC 的「管理员 / 版主 / 普通用户」三级在端内是**能真的干活**的，不是一句文字说明。
  - **「我的」页**：角色**徽章** + 「我的权限」卡 + **管辖范围**块（管理员「全站」/ 版主「仅限《某个游戏》」）+ **权限矩阵**。
    ⚠️ 卡片上**不再另外罗列一份「能做哪些事」的文字摘要** —— 能力清单只在矩阵里出现一次（见下），避免两套文案重复且各自漂移。
    矩阵按 **「小程序端内可直接操作」/「仅主站管理后台提供」两组**呈现（哪几项能在手机上点、哪几项必须回主站看，一眼可辨），
    默认**折叠**、标题栏给摘要「小程序内 3/5 · 主站 2/6」（以版主为例），点一下展开 11 项逐条 ✓ 可用 / ⊘ 仅管理员。
  - **帖子详情页**：按角色显示「管理」入口，且**按帖子所属游戏判作用域**——
    - 管理员：任意帖子都能管（置顶 / 加精 / 隐藏 / 恢复）
    - 版主（**自己负责的游戏**）：加精 / 隐藏 / 恢复（**无置顶**，置顶是管理员专属）
    - 版主（**别的游戏**）：**没有管理入口**，并提示「不在你的管辖范围」
    - 游客 / 普通用户：看不到入口，也**不会发起任何管理接口请求**
  - ⚠️ **「审核帖子（通过 / 驳回）」归主站，端内不做**（2026-09-27 更正口径）：
    详情页管理面板里虽写了这两个动作（只在待审帖出现），但**端内没有任何路径能把人送到一篇待审帖面前**——
    端内列表只呈现公开帖（`status=0`），没有「待审核列表」页（`pages.json` 只注册了 `admin/users`、`admin/reports`），
    举报队列页不跳被举报帖，端内也没有通知中心 ⇒ 管理员在手机上**永远点不到**这两个按钮。
    因此矩阵如实标注为「主站」，真正的审核在主站管理后台完成（后端 `/admin/posts/{id}/approve|reject`
    与 `canReviewPost`「自己不能审自己」的规则不变，端内凭证直连同样受 `@PreAuthorize` 保护）。
  - **👥 管理员「用户权限管理」页（`pages/admin/users.vue`）**：管理员在端内即可
    **搜索用户**（用户名 / 昵称模糊匹配）→ 查看并**修改角色**（普通用户 / 版主 / 管理员，单选，与主站口径一致）
    → 选「版主」时指定**负责的游戏**（一名版主限 1 个）。改完**即时生效**，对方无需重新登录。
    - 非管理员进入该页只显示「仅管理员可访问」，且**一个请求都不会发**。
    - **自保**：不能摘掉自己的管理员角色（前端直接禁用保存 + **后端也拒绝**）；自己被标「你」，面板给出风险提示。
  - **🚩 举报处理页（`pages/admin/reports.vue`）**：把「处理举报」从主站搬进端内，**管理员与版主共用同一个页面、同一套接口**，
    作用域由后端按游戏切分：
    - **管理员** → 看到**全站**举报（含「举报用户」这类无游戏归属的）
    - **版主** → 只看到**自己负责游戏**下的帖子 / 回复举报，页头如实写明「仅你负责的《某游戏》」
    - 状态筛选：待处理 / 已处理 / 已驳回 / 全部；条目显示举报理由、被举报内容、**归属游戏与板块**、举报人与时间
    - 处理动作两段式（选动作 → 就地二次确认）：**「标记违规」**（后端会连带隐藏被举报的帖子 / 回复并同步计数，不可撤销）
      / **「驳回」**（仅结案，内容保持原样）；可填处理备注
    - **点不动的地方一律提前置灰并说明原因**：「举报用户」仅管理员可处理、目标已删除无法处理、已结案不能重复处理
      —— 而不是让人点了再吃 403 / 400
  - ⚠️ **端内只决定「显示什么」，判定永远在后端**（`@PreAuthorize` + 游戏归属校验）：用普通用户的 token 直连管理接口，后端一样返回 **403**。
  - 📊 **两个角色的差异是可量化的**：管理员可执行 **11 / 11** 项能力，版主 **5 / 11**（且版主的能力**全部限定在自己的管辖范围内**）。
- **🤖 AI 智能助手（新增）**：首页与「我的」页均有入口，进入独立聊天页，复用后端 `POST /api/ai/chat` 的 **SSE 流式**回答；支持快捷问法、Markdown 富文本渲染。后端无改动，仅前端补齐入口与流式渲染。

**技术形态**：uni-app + Vue3（`<script setup>`），一套代码同时产出**微信小程序 + H5**；状态管理用模块级 `reactive` 单例（不引 Pinia，场景够用且更轻）。

### 后端（对应作业要求 D）
- **spring 相关框架**：Spring Boot 4.0.8 + Spring Security（认证/授权）。
- **mybatis-plus**：`mybatis-plus-spring-boot4-starter` 3.5.17，全量 CRUD + 分页 + 逻辑删除。
- **redis**：缓存服务（`RedisCacheServiceImpl`）+ 限频（`RateLimiter`）；AI 多轮会话历史也存 Redis。
- **权限方案**：Spring Security + JWT + RBAC（管理员 / 版主 / 普通用户，`role` / `user_role` / `moderator_board` 三张表），接口级 `@PreAuthorize` + **游戏归属校验**（版主仅限自己负责的游戏；一名版主最多负责 1 个游戏，管理员为全站）。角色数据（`roles` / `badge*` / `moderatorGameIds` / `moderatorGameNames`）通过 `GET /api/auth/me` 下发，**小程序端据此按角色渲染并判定管辖范围**（见上），且所有管理操作写审计日志。
  - 权限判定分两级且**语义不同**，这是实现时最容易踩的地方：`canReviewPost`（审核通过 / 驳回用，含「**自己不能审自己**」）vs `assertCanModeratePost`（加精 / 隐藏 / 恢复用，**无**此限制）。
  - **自保**：`updateUserRoles` / `setUserStatus` / `deleteUser` 均**拒绝「操作自己」**（角色那条只拦「摘掉自己的 ADMIN」）。
    必要性：JWT 过滤器每次请求都按 uid **重新查库**取角色 ⇒ 自己一降级，手上的 token **下一跳即失效**、后台从此无人可进（且不可逆）。
    ⇒ 反向也是一个特性：**权限变更即时生效，不需要对方重新登录**。
- **微信小程序前端**：uni-app 编译到 mp-weixin（见上）。
- **AI 功能引入**：`AiAssistantController`（`POST /api/ai/chat` SSE）+ `AiAssistantService`（调 OpenAI 兼容接口，知识库 `ai/*.md` 兜底），前端（主站 + 小程序）流式消费。

## 七、已知边界（避免误解）

1. **不上架微信**：上架需要「HTTPS 域名 → 域名 ICP 备案 → 小程序备案 → 类目审核」四关，本项目只有 IP、未备案，第 1 关就过不去。故交付形态为 **H5 版 + 开发者工具预览 + 可选体验版**（体验版同样需要每个成员首次手动开一次调试）。
2. **微信内置浏览器（XWeb）未实测**：回归跑的是 Chromium，与微信内置内核可能有细微差异。
3. **数据依赖线上后端**：若 `8.133.255.202` 不可达且未本地起 jar，小程序界面将无内容（非程序缺陷）。
4. **AI 回答由大模型实时生成，可能不准确**，页面已注明「以社区内容为准」。
